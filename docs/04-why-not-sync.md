# 04 · 为什么**不做**同步

[English](04-why-not-sync.en.md) ｜ 中文（本文）

这份文档记录被否决的方案和理由。写下来是因为：几乎每个看到"双系统 + 一份数据"的人，第一反应都是"上个同步工具不就完了"。

---

## 0. 决定性的前提

> **这是一台笔记本，装了双系统（macOS + Windows）。同一时刻只有其中一个系统在运行。**
> Windows 开机时 macOS 必然是关机的，反之亦然。

由此推出三件事：

1. **不存在并发写** —— 两端不可能同时持有这个文件。
2. **不存在数据分叉** —— 没有"两端各自改了同一行"这种事，因为没有两端。
3. **唯一需要防的，是"信任错位"** —— 后开机的一端起手就假设"文件是好的"，然后在这个假设上继续写。

所以：**同步算法解决的是"分叉"，而这里没有分叉。** 上同步工具是在用一个很重的机制解决一个不存在的问题，同时**引入**了它自己的新问题（见下）。

---

## 1. ❌ 两端各存一份"工作副本"，退出时合并

**否决理由**：需要一个真正的合并算法。数据库不是文本——同一行在两端被改，合并要么靠业务主键 + 时间戳（时间戳在这个文件系统上不可信，见 [01·A3](01-failure-modes.md#a3-时间戳粒度-2-秒且跨系统不可比-实测--推理)），要么靠 CRDT（得改应用的数据模型）。而只要有合并逻辑，就一定有"合并错了但没人发现"的路。

**更根本的**：这个方案的前提是"有两份数据需要对齐"。在互斥前提下，**这个前提是假的**。

## 2. ❌ 快照链当传输通道（`gen0001.db → gen0002.db → …` + manifest）

**否决理由**：这是我最早想到的方案，被自己否掉了。它把"当前状态"变成了"一串历史"，于是每次开机都要回答"我该从哪一代接上"——这个问题需要 manifest 与快照之间的信任链，而 manifest 本身也在同一个不可靠的卷上。绕一圈，**信任问题一点没减少，反而多了一层状态**。

保留的部分：现在协议里的 `snapshots/` **只做回滚锚点**（2 代），不做传输通道。当前状态永远只有 `db/state.db` 一个。

## 3. ❌ Syncthing / rsync / 网盘同步

**否决理由**：

- 它们假设"两端同时在线"，在双系统上**永远只有一端在线**，同步队列会变成"每次开机先跑一轮历史变更的重放"。对一个 145 MB 的单一二进制文件来说，这一轮经常变成整文件传输。
- 它们的冲突处理对二进制文件基本是"保留两份"，于是你会得到 `state.sync-conflict-20261026.db`——**两个数据库文件，哪个是对的没人知道**。
- 最关键：**它们不知道 SQLite 需要"WAL 已合并"才是一个完整状态**。同步一个正在被写的库，等于同步半个事务（见 [01·B1](01-failure-modes.md#b1-库锁不能跨启动只能跨进程-实测--推理)）。

## 4. ❌ git

**否决理由**：单个二进制大文件的每次提交都是全量副本；仓库会迅速膨胀到几个 GB；而 git 的合并能力对 SQLite 文件**完全无效**（一行都合不了）。何况把私人数据库提交进仓库本身是隐私事故。

## 5. ❌ 导出成 markdown / JSON 文本，双端各存一份

**否决理由**：文本格式确实能 diff 能合并，但**应用未必能可靠导入回来**，而且导入导出会丢字段（embedding、时间序列、内部 ID、外键）。一旦两端都从对方的文本重建，等于让应用"重新认识"自己的数据——任何有状态的字段都会漂。

**这一条曾经看起来很美**，因为 `*.md` 天然可读、可版本化。但它把"数据完整性"换成了"人类可读性"，而这个库的价值恰恰在完整性。

## 6. ❌ 换个文件系统（把库放 NTFS，或放 APFS）

**否决理由**：

- **APFS / HFS+**：Windows 读不了（没有任何可靠的量产读写驱动）。
- **NTFS**：macOS 只能只读（原生）；第三方驱动（Paragon / Tuxera）是**内核扩展**，在黑苹果上是另一整类风险（SIP、kext 签名、系统更新后失效）。
- **exFAT**：两端都原生读写 —— 这就是它被选中的唯一理由。代价是本文档前面写的全部内容。

> **如果你真的在乎数据、且能接受代价**：把库放在各自系统的原生分区上，用**复制 + 校验**在关机/开机时搬运（也就是本协议的做法），而不是让两端直接打开共享盘上的文件。这样至少**文件系统损坏不会同时是"我的唯一副本坏了"**。代价是需要 2 倍的磁盘空间和一次 1~2 秒的复制（实测 152 MB ≈ 1.2 秒）。
>
> 这条是本协议的一个变体，**没做**，因为用户明确要求"两端直接读同一份物理文件"（不想有工作副本）。把它写在这里，是因为它确实是更安全的选择——只是更啰嗦。

---

## 7. 如果以后有了第二台机器，什么会变

上面所有"不需要同步"的结论，**全部依赖于"同一时刻只有一个系统在跑"**。一旦满足下面任何一条，本文档就不适用了：

- 两台机器可能同时开机（哪怕只是"手机 App 也能写"）；
- 同一个系统上多个应用进程会同时写；
- 数据被放到网络上（NAS / 云盘 / 共享文件夹）。

那时你需要的不是这份协议，而是：**单写者服务端 + 客户端只读缓存**，或者**应用层真正的冲突解决（CRDT / 操作日志）**。搬文件是解决不了并发写的。

---

## 8. 所以这个方案的定位

> 它不是在"同步数据"，它是在**给一次交接盖章**。
>
> 因为双系统已经把最难的并发问题替你解决了，剩下的全部工作量，就是把"我能不能信这个文件"这个问题，用**一个哈希、一个收据、一个脏标志**回答清楚。

如果一个方案让你觉得"几乎什么都没做"，那大概是对的 —— 在互斥前提下，正确的做法本来就很轻。**重点不在代码量，在于那三个文件的位置和顺序。**
