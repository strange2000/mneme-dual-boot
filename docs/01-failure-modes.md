## A. 文件系统层（exFAT 本身）

### A1 没有日志，损坏是**卷级**的 [实测·部分]
FAT/exFAT 的目录项和簇链不是事务性更新的。断电或强拔时，exFAT 可能留下：

- 文件名在、内容变成 0 字节；
- 文件大小正常，但簇链指向错误的簇（内容变成别人的数据或一长串 `0xFF`）；
- 目录项半写（文件名乱码）。

macOS 下次挂载会跑 `fsck_exfat`，它**会自己"修"** —— 修法通常是丢弃它认为不一致的簇链。也就是说：**你可能在还没打开数据库之前，就已经被文件系统悄悄改过一次了。**

这与 NTFS/APFS 有日志的情况本质不同：那边崩溃后最坏是回滚到最后一次事务；这边最坏是文件结构本身坏掉。

### A2 权限是假的 [实测·Windows + 实测·macOS]
Windows 侧：`chmod 0600` 之后实际 `mode = 666`。
macOS 侧：mode **恒为 `0o700`**，`chmod 600` / `777` / `000` 都不改变任何东西、也不报错，`chmod 000` 之后文件照样读得出来 —— **chmod 是彻底的空操作**，根因是挂载带 `noowners`。同一个卷上的东西，这台机器上任何能登录的账户都能读写。

**没有任何办法在 exFAT 上给单个文件加权限。** 要么把整个卷做成加密卷（VeraCrypt / BitLocker To Go，注意 macOS 侧要能读），要么承认它。

> ⚠️ **macOS 上这个坑会伪装成"权限有效"。** `lab/exfat-probe.mjs` 自带的 `permissions_enforced` 判断的是 `mode & 0o077 === 0`，而 macOS 无条件报 0700，于是它在 macOS 上报了 `true`。要判断权限有没有生效，只能看"chmod 之后 mode 变不变"和"chmod 000 之后还读不读得到"，不能看 mode 的绝对值。

### A3 时间戳粒度：Windows 2 秒，macOS 10 毫秒 [实测]
同一块卷、同一份 exFAT 规范，两端驱动给出的粒度差 **200 倍**：

| 端 | 粒度 | 测法 |
|---|---|---|
| Windows | **2.000 s** | 5 秒内 20 次写入只产生 4 个不同 mtime |
| macOS | **10 ms** | 200 次连续重写产生 78 个不同 mtime，正步长恒为 10.000 ms（最小 = 中位 = 最大） |
| APFS（同机对照） | 亚毫秒 | 200 次重写 200 个不同值 |

10 ms 正好是 exFAT 规范里 mtime 的存储单位，所以**macOS 是照规范做的，2 秒是 Windows 驱动的实现问题** —— 别把它当成"exFAT 天生如此"。

[推理，未在本机对照测过] 更麻烦的是语义：FAT/exFAT 的时间戳是**本地时间**字段，Windows 按本地时区写、macOS 多以 UTC 解释。跨双系统时，同一个文件在两端的 mtime 显示可能差整数小时，且夏令时切换会让差值改变。

**结论：mtime 在两个用途上都不可用**——不能用来排序，也不能用来判断"变没变"。两端粒度差 200 倍，意味着你在这端看到的"没变"，完全可能是那端刚写完。

### A4 大小写不敏感 [实测]
`CaseProbe.TXT` 与 `caseprobe.txt` 是**同一个文件**。写后者直接覆盖前者，两个名字都还在。

任何"按大小写区分副本""按规范化路径去重""校验路径拼写"的逻辑，在这个卷上都是错的。

### A5 符号链接：Windows 不行，macOS 行；硬链接两端都不行 [实测·Windows + 实测·macOS]
Windows 侧：`fs.symlinkSync` / `fs.linkSync` 均失败，`EISDIR`，`errno = -4068`。
macOS 侧：**符号链接能建** —— 绝对路径和相对路径都可以，`readlink` 能还原，能跟随读取（内容一致），`lstat` 报 `Symbolic Link`，而且**没有 `._*` 伴生文件**（驱动层直接表示）；**硬链接不行**，`ENOTSUP`，`errno = -45`。

所以"卷内不能做 `current → gen0007.db` 这种指针布局"这个判断**只对 Windows 成立**。macOS 上可以做，但两端布局就对不齐了：Windows 端建不出来。

> 注意区分：**从 NTFS/APFS 指向 exFAT 的符号链接两端都可以**（Windows 侧就是 `mklink`）。本机的 `~/.dsh/memory` 正是这样一个链接，指向共享卷上的库目录。
>
> ⚠️ **未验证**：Windows 能不能读 macOS 建在 exFAT 卷里的软链。exFAT 规范里没有软链的表示法，macOS 的驱动是自己扩展出来的 —— Windows 驱动很可能只把它当成一个普通文件，或者直接报错。**不要把协议布局建立在它上面。**

协议里的"发布"动作因此仍然只能建立在 `rename` 上。

### A6 分配单元 128 KiB [实测]
写一个 1 字节的文件，实际占用 131,072 字节。数百 GB 级的 exFAT 卷上这是默认的大簇。

**后果**：不要在这块盘上做"每次交接存一堆小文件"的设计。快照要么是大文件（正常），要么别做。

### A7 两端的隐藏垃圾文件 [实测]
macOS 在卷根写 `.Spotlight-V100`、`.fseventsd`、`.TemporaryItems`、`.Trashes`，并为带扩展属性的文件写 `._文件名` 伴生文件；Windows 写 `System Volume Information`、`$RECYCLE.BIN`、有时还有 `msdownld.tmp`。这台机器的共享卷根目录上，这些**全都有**。

**后果**：任何"遍历目录、把所有文件都当成数据"的逻辑都会踩到它们；备份/哈希工具要显式排除。

## B. SQLite 层

### B1 库锁不能跨启动，只能跨进程 [实测 + 推理]
实测：在 exFAT 上，一个进程持有 `BEGIN IMMEDIATE` 时，另一个进程在 `delete` 和 `wal` 两种模式下都拿到 `database is locked`。**锁是好的。**

但锁是**内存态**的（由操作系统文件锁实现）。OS A 强关机时没释放的锁，在 OS B 看来**根本不存在**——因为锁表在 A 的内存里，随断电消失了。

所以：
- 同一系统内，靠应用的 SQLite 锁防双写 ✔
- 跨系统/跨启动，**只能靠持久化的脏标志**，不能靠锁

### B2 WAL 是一份额外的、必须一起搬运的状态 [实测]
`-wal` 里是**尚未合并进主库的事务**。热拷贝主库而不管 `-wal`，你拿到的就是"WAL 之前的视图"。

实测数字：数百 MB 级的主库旁挂着 **数 MB 的 `-wal`**。

- 干净关闭时 SQLite 会自己 checkpoint 并删掉 `-wal`/`-shm`（实测：关闭后两个文件都不存在了）
- 崩溃/强杀时**不会**（强杀后的现场见 B5 的反常记录）

**规则：交接的第一步永远是 `PRAGMA wal_checkpoint(TRUNCATE)`，然后确认 `-wal` 真的是 0 字节或不存在。**

### B3 崩溃后残留的 `-journal` 可能回滚失败 [推理]
`journal_mode=delete` 下崩溃会留下 `-journal`，SQLite 下次打开会拿它回滚。但如果这个 `-journal` 本身是在崩溃中被截断/半写的，回滚可能失败，典型的报错是 `database disk image is malformed`。

这也是为什么"交接前强制 TRUNCATE + 体检"比"指望下次自动恢复"更可靠：**把不确定性留在这一次，而不是留给下一次开机。**

### B4 `integrity_check` 通过 ≠ 数据完整 [推理，但很重要]
`integrity_check` 查的是**页结构与索引一致性**，它不知道"昨天那 300 条记忆应该还在"。

主库页面上**没有校验和**（只有 WAL 帧里有）。单个页面被写坏，在你读到那一页之前毫无征兆。

所以体检只能证明"结构没坏"，证明不了"内容没丢"。要证明后者，需要：
- 每次交接记一个**内容摘要**（表行数、关键表的最大 gen/更新时间）；
- 或者定期做一次全量 `integrity_check` + 抽样读；
- 以及**保留上一代快照**，让"丢了一批"至少可以人工比对。

### B5 ~~一个反常现象（没能解释）~~ 已查明：是 V8 的 GC，不是卷 [实测]
> 订正：本节早期版本把这个现象记成"提交 50 次 / 主文件 8192 字节"，实际 `lab/crash-probe.mjs` 提交的是 **500 次**、主文件 **16,384 字节**。数字一并更正；现象本身是真的，只是当时归因错了。

原记录：子进程以 WAL 模式提交 500 次、不关闭、被 `SIGKILL` 之后，磁盘上**没有 `-wal`**，另一个进程却能读到 500 行，`integrity_check` = ok，`journal_mode` 仍报 `wal`。当时怀疑是 node:sqlite 的连接参数，或这个卷的写缓存。

**真实原因：`node:sqlite` 的连接会在 `DatabaseSync` 对象被 GC 回收时关闭。** 那个子进程写完信号文件就开始空转，之后再没引用过句柄，句柄于是变成不可达 → 被回收 → 连接被关闭。而对 SQLite 来说，最后一条连接关闭就是一次**干净的 close**：先把 WAL checkpoint 进主文件，再删掉 `-wal`/`-shm`。父进程采到的正是"关闭之后"的终态，于是看起来像 WAL 帧被卷直接吞了。

[`lab/b5-gc.mjs`](../lab/b5-gc.mjs) 是一键复现的 A/B/C（`node lab/b5-gc.mjs <目录>`）：

| 变体 | exFAT | APFS |
|---|---|---|
| A：`h` 之后不再被引用（原样） | `-wal` 消失 **3/3** | 消失 **2/2** |
| B：加一句 `globalThis.__keep = h` | 消失 **0/3** | 消失 **0/2** |
| C：显式 `h.close()` | 消失 3/3，盘上终态与 A 一致 | 同 |

唯一变量是 JS 句柄是否还被引用。文件系统、`journal_mode`、`synchronous`、显式事务都被分别排除（那些组合下 `-wal` 始终 2,080,632 B、主文件始终 4,096 B）；APFS 上结论相同，所以"卷写缓存"和"连接参数"两个候选解释都可以删掉。

两条后果：**数据没丢**（GC 触发的是干净 close，500 行都在主文件里，危险的是推论不是数据）；**进程活着 ≠ 库还开着**（进程可以不退出就把库关掉，`ps` 仍显示 `R`，但那一瞬间 `lsof` 里一个 `state.db` 都看不到）。

**结论比原来更硬：不要把"有没有 `-wal`""`-wal` 有多大""主文件多大"当成任何判断依据，也别拿"进程还在不在"推断"库还开不开"。** 判活要用 `lsof +D <目录>`（macOS 的 exFAT 上实测可用，能直接列出 `state.db` / `state.db-wal` 的持有者），不要用 `kill -0`。只信你自己算的哈希、你自己跑的 `integrity_check`、和你自己写的收据。

## C. 时序层（这一层最要命）

### C1 陈旧信任：下一端无条件相信上一端 [设计问题]
两端不会同时开机，所以**不存在"数据分叉"**。存在的只有一种失误：**B 端打开了一个 A 端没好好封口的文件，并且在上面继续写。** 一次就够。

这就是 `DIRTY` 标志存在的全部理由。

### C2 回滚是静默的数据删除 [设计问题]
回滚到"上一份好快照"听着很安全，但它是**把新数据扔掉**。必须满足：

- 回滚前把当前库**改名保留**（`state.db.abandoned-<时间>`），不删除；
- 回滚写进日志，并且**在下次开机时主动告诉用户"我回滚了，旧数据在哪个文件"**；
- `gen` 不因回滚而倒退（回滚也 `+1`，并标记 `rollback: true`），否则代次失去单调性。

### C3 应用没退出 [实测经验]
Windows 上文件被句柄占用时，很多操作会以**奇怪的方式**失败（不是干净的 EBUSY）。曾经的典型事故是"以为退出了，其实托盘里还有进程，两个进程在写同一个库"。

必须**判活**，而且判活必须是"能独占打开这个文件"，不是"任务管理器里看起来没有它"。

### C4 卷没挂载 / 挂载到别的路径 [常见]
双系统下共享卷的盘符/挂载点在两端不同，且可能因为顺序变化而变。协议必须**按卷序列号或 UUID 认卷**，不能按盘符/路径认。

## D. 人为层

| # | 事故 | 后果 |
|---|---|---|
| D1 | 两端各存一份"工作副本"再合并 | 需要真正的冲突解决；合并逻辑一错就是丢一批 |
| D2 | 手动复制时忘了 `-wal` | 静默丢最后一段事务 |
| D3 | 复制到一半卷满 / 中断 | 半截文件被当成完整库；exFAT 上失败不一定会删掉目标文件 |
| D4 | 把库提交进 git | 隐私外泄 + 仓库巨大；而且 git 的合并对这个文件毫无意义 |
| D5 | 两端应用版本不同 | schema 迁移通常是单向的，回退会出事 |
| D6 | 用"最近修改时间"决定保留哪份 | 见 A3：粒度 2 秒（Windows）/ 10 毫秒（macOS）、跨系统偏移，判断基本靠运气 |

## 未验证清单（诚实边界）

以下我**没有**测，原因是要么没有对应环境，要么会真的毁掉我自己的库。macOS 侧后来补测的条目就地标注了：

1. **macOS 侧的崩溃 / 修复行为**：exFAT 驱动在强关机后的卸载行为、`fsck_exfat` 实际会怎么"修"、Spotlight / `.fseventsd` 是否会在应用写入时触碰数据库。（macOS 上**已实测且可依赖**的部分：`lsof +D <目录>` 能准确列出 `state.db` / `state.db-wal` 的持有者；这些探针也没有在卷上产生 `._*` 伴生文件。）
2. **真断电 / 真拔盘**：所有"崩溃"结论都来自 `SIGKILL` 强杀进程。强杀只影响**文件内容层**，断电还会影响**文件系统结构层** —— 而 exFAT 恰恰在后者没有日志。**请按"最坏情况比本文更糟"来读。**
3. **exFAT 卷满时的行为**（是否原子失败、是否留下半截文件）。
4. **长时间运行后的大库表现**（本文只在 145–148 MB 规模测过）。
5. ~~**B5 的反常现象**的成因。~~ → **已查明**，见 B5：V8 GC 回收 `DatabaseSync` 导致连接被关闭。
6. **跨系统的 mtime 语义差**（A3 的推理部分）。→ 粒度已测（Windows 2 s / macOS 10 ms / APFS 亚毫秒），**语义差（本地时间 vs UTC 解释）仍未验证**。
7. **Windows 能否读 macOS 建在 exFAT 上的软链**（见 A5）—— 新增的未验证项。
8. **WAL 库在不可写目录下的只读打开**：macOS 上会报 `unable to open database file (14)`（建不了 `-shm`），只有 `?immutable=1` 能打开但它会忽略 WAL —— 已写进 [`03`](03-recovery-runbook.md)，但"整个卷只读挂载"这种更极端的情形未测。

如果你在 macOS 侧测了其中任何一条，请开 issue —— 这是这份文档最缺的东西。
